## 1. Objetivo

Que el juego se pueda jugar de principio a fin dentro del editor, sin red:
menú → partida → 3 vidas → game over → reintento, con puntaje y colección.

### 2.2 Reglas del juego

| Elemento | Valor | Dónde |
| :--- | :--- | :--- |
| Vidas iniciales | 3 | `GameManager.startingLives` |
| Duración | 120 s | `GameManager.matchDurationSeconds` |
| Ítems buenos | +10 a +25 pts | `ItemCatalog` |
| Peligros (erizo, medusa) | −1 vida | `ItemCatalog` |
| Basura | −10 pts, sin vida | `ItemCatalog` |
| Dificultad | intervalo 0.95 s → 0.38 s; caída 3.6 → 7.5 u/s | `ItemSpawner` |
| Récord | `PlayerPrefs` (`ct.best_score`) | `GameManager` |

> El puntaje local **nunca** es el definitivo: en F5 el backend valida una firma
> HMAC y descarta envíos alterados (A.8.9 y A.8.24).

## 3. Herramientas y flujo de trabajo

| Necesidad | Herramienta | Nota |
| :--- | :--- | :--- |
| Compilar y detectar errores | `Unity.exe -batchmode -quit -executeMethod …` | Más fiable que el MCP para compilar |
| Corrección automática | `-runTests -testPlatform PlayMode` | Devuelve XML de resultados |
| Editar escena en vivo | Unity MCP (`manage_scene`, `manage_editor`, `execute_code`) | Recuperado tras fijar `MCPForUnity.AutoStartOnLoad` |
| Compilación en Unity | `CosTamarindo.asmdef` + `CosTamarindo.Tests.PlayMode.asmdef` | Separa runtime, tests y editor |

### 3.1 Hallazgos del entorno

1. **El puente MCP no arranca solo** si `EditorPrefs["MCPForUnity.AutoStartOnLoad"]`
   está en `false`. Se reactiva con `EditorBootstrap.EnableMcpAutoStart()` en batchmode
   (helper `Assets/Editor/EditorBootstrap.cs`).
2. **`execute_code` (CodeDom) no acepta `using`**: usar tipos calificados.
3. **El bucle de juego se congela sin foco**: se corrige con
   `Application.runInBackground = true` en `GameManager.Awake` (el ajuste de
   Player Settings no basta en el editor).
4. **Capturar pantalla del editor no es fiable** si la ventana no tiene foco:
   para verificar arte se renderiza la cámara a un `RenderTexture`.
5. **Unity tarda varios minutos** en reimportar la Library tras renombrar la
   carpeta del proyecto (cambian las rutas absolutas de los artefactos).

## 8. Corrección 2026-10-28 · el spawner no arrancaba

**Síntoma.** En el build WebGL no caía ningún ítem: la partida se podía mover pero no había
nada que atrapar. `Spawner_ProducesItemsWhilePlaying` falló de forma determinista
(*«Expected: greater than 0 / But was: 0»*).

**Causa.** `ItemSpawner` se suscribía a `GameManager` en `OnEnable`. Unity no garantiza el
orden de `Awake`/`OnEnable` entre objetos, así que el spawner podía activarse antes de que
`GameManager.Instance` existiera: nunca recibía `StateChanged`, `running` se quedaba en `false`
y `Update` salía en la primera línea. Los otros tres tests pasaban porque llaman a
`GameManager` directamente, sin pasar por el spawner.

**Corrección.** Suscripción perezosa e idempotente:

```csharp
private void TrySubscribe()            // en OnEnable, Start y Update
{
    if (subscribed || GameManager.Instance == null) return;
    GameManager.Instance.StateChanged += HandleStateChanged;
    GameManager.Instance.MatchEnded   += HandleMatchEnded;
    subscribed = true;
    HandleStateChanged(GameManager.Instance.State);   // sincroniza si ya estaba jugando
}
```

**Verificación.** Tests PlayMode verdes (hoy **6/6**) y build WebGL regenerado: los ítems caen en el
navegador (`evidencias/F3/screenshot-game.png`).

**Lección.** Un test de humo debe comprobar el efecto observable (hay ítems), no solo que los
objetos existan. Los tests que llaman métodos del manager no cubren el cableado de la escena.

## 9. Arte de Figma en la escena · 2026-10-28

Se sustituyeron los placeholders por el arte real exportado del archivo
[CosTamarindo en Figma](https://www.figma.com/design/qI8jr7abLu6tIpL0MnL8Ol/CosTamarindo?node-id=0-1&t=p2hEW0NuUDtfsm9e-1).

| Cambio | Detalle |
| :--- | :--- |
| Personaje | `palenquera.png` (592×637) en `Player/Visual`, PPU 100, pivote abajo-centro |
| Altura en pantalla | 3 unidades de mundo (30 % de la cámara), pies en `y = −4.6` |
| Animación | `CharacterAnimator`: paso con rebote, inclinación de 7°, aplaste de 3,5 %, respiración en reposo y volteo según la dirección |
| Captura | `CatchHeight` calculado desde el borde superior del sprite: la línea queda en la **canasta**, en `y ≈ −1.88` |
| Fondo | `bg_playa.png` (1935×1106) en `Background`, `sortingOrder −100`, escalado *cover* con `BackgroundFitter` |
| Sombra | Elipse difusa generada en runtime bajo los pies |

**Por qué la animación es procedural.** Figma solo entrega una pose de la Palenquera; no hay
hoja de sprites. Reproducir un ciclo de caminata con una sola imagen obliga a mover el sprite
(bob + tilt + squash), que es exactamente lo que hace `CharacterAnimator`. Cuando exista una
hoja de sprites, se cambia por un `Animator` y `PlayerController` no se toca.

**Riesgo asumido.** Al no haber poses, la animación no tiene piernas articuladas: se lee como
"la niña camina contoneándose". Es suficiente para el vertical slice y no bloquea F2.

**Verificación.** Escena regenerada con `CosTamarindo → Construir escena de juego`, consola sin
errores, **6/6** tests PlayMode (se añadieron dos: línea de captura en la canasta y fondo que cubre
la cámara) y capturas del build WebGL en `evidencias/F3/`.
